## What was found in the code

Four findings changed the plan. All were measured, not assumed.

**There is no transportable AlgoHex.** `external/algohex-src/Dockerfile` has a
working-tree modification that comments out upstream's build:

```diff
-RUN cd /app/build && ninja
-RUN ln -s /app/build/Build/bin/* /usr/local/bin
+#RUN cd /app/build && ninja -j1
+#RUN ln -s /app/build/Build/bin/* /usr/local/bin
```

The compile was run by hand into the Docker volume `algohex-build-cache`,
plausibly because a non-resumable single-layer `ninja -j1` on 2 vCPUs takes
hours. Volume contents are not part of an image, so `docker save` produces an
image without `HexMeshing`. This blocks every cluster route, for enroot and
Apptainer alike, and it is also a single point of failure — see the backup
section below.

**The frame field is the wrong source for curved edges.** It is never written
out: `run_algohex.py` saves the seamless map and the post-singularity tet mesh,
and `DATA_GENERATION.md` already measured that the latter is binary OVM which
AlgoHex's own reader rejects. Beyond that, a frame field is a per-tet
*direction*, not a curve, and it is the stage that produced the hex mesh — so
it is the upstream source, not the better one. The block edges are already
polylines of ~25 fine-mesh vertices tracking the geometry to 0.006, and
`curved_refill._cubic_axis` fits them in one call.

**The 2D edge-representation study does not transfer.**
`06_edge_geometry_study.md` chose chord-local `cubic_bezier` for being shorter
and invariant. Counted in 3D, the length advantage vanishes — 6 scalars for
absolute control points, 6 for chord-local, 10 for Hermite — and chord-local
becomes ambiguous, because the space perpendicular to a chord is a plane rather
than a direction. The transverse frame would need a canonical rule, and every
simple rule degenerates on exactly the edges this geometry has most of:
`DATA_GENERATION.md` measures one radial direction class threading every block
in every sample.

**enroot works here; SLURM does not.** enroot 4.2.0 is installed, with
`squashfuse` and `mksquashfs`, on a KVM VM with uid 0, `/dev/fuse`,
`unprivileged_userns_clone = 1`, and both `unshare -U -r` and `unshare -m`
succeeding. So `enroot import` and `enroot start` can be verified locally. What
cannot: SLURM (no `sbatch`/`srun`, hence no pyxis, which is a SLURM plugin) and
the Lustre transfer rates that dominate cluster job time — 5-10 MB/s per
`eigenfrequencies/docs/cluster-dtoo-enroot-befund-v2.md`, so `enroot create`
from an 8 GB image costs 14-27 minutes per job there.

Note that the earlier statement "enroot cannot be tested here" was true when it
was made: `duty/quadmesh/scripts/dryrun_planb.slurm` records that its scripts
arose "in einer Umgebung ohne Cluster-Zugang (kein sbatch, kein enroot, kein
SSH zu uc3)". enroot has been installed since.

## Two assistant claims corrected during the session

1. **"Block-size uniformity is the lever for the first-order route, so the two
   routes need different collapse depths."** Wrong. The 2D route already solves
   this by subdividing the coarse higher-order blocks
   (`meshtron/augment_subdivide.py`, `export_augmented.py --ns 2 3 4`, 7 988 →
   ~31 900 meshes). Subdivision is a post-process on the finished artifact,
   costs seconds, and produces the uniformity directly. One structure, both
   routes.
2. **"Apptainer is the bwUniCluster standard."** A generalisation, and wrong
   for this account. The proven stack there is enroot with pyxis:
   `eigenfrequencies/cluster/enroot_dtoo_import.md` is titled "dtOO enroot
   import guide — bwUniCluster 3.0", and shell history from nodes
   `uc2n602`/`603`/`605` shows `enroot start --root -m ... dtOO.sqsh` against a
   5.8 GB workspace image, with `enroot list` reporting a pyxis container.

## The arithmetic that shapes the pipeline

Two numbers decide the cost of the dataset, and both were already in
`DATA_GENERATION.md` without their consequence being drawn.

**`-n` costs AlgoHex almost nothing and dominates our stage.** AlgoHex takes
12.2 / 10.7 / 10.3 minutes at n = 2000 / 8000 / 60000, because the
parametrization computes a map and quantization scales it afterwards. The sheet
collapse takes ~1 / ~3 / ~45 minutes, because it iterates over cells.
Therefore:

```
n=60000 alone      55 min  ->  1 structure
n=2000 and n=8000  27 min  ->  2 structures
```

And the two are not duplicates: n=2000 reproduces v11 exactly (16 blocks, 14
cuboids, 11 classes) while n=8000 gives 19 blocks with 9 classes and no pinch.
Distinct valid decompositions of the same domain — which is the right lesson
for a generative model, since a geometry does not have one correct block
structure.

**The gate on that is the curve fit.** A block edge carries about 25 points at
n=60000 and about 4 at n=2000, the bare minimum for a cubic. Measuring the fit
residual on structures that already exist on disk decides whether a sample
costs 13 minutes or 55, and whether anything at all fits into bwUniCluster's
30-minute `dev_cpu_il` slot.

**Storage.** A finished sample is ~90 MB today, of which `blocks.vtk` (4.8 MB)
and `tet.vtk` (2.3 MB) are the only parts that cannot be recomputed in seconds.
Keeping those two plus the ~1 MB sample file is ~8 MB, so 80 GB at 10 000
samples against 900 GB for everything.

## Backup situation, measured 2026-09-11

Checked because the AlgoHex finding above raised the question. This is T0 in
`DATASET_PIPELINE.md` and should be done before anything else.

| asset | where | backed up | reproducible |
|---|---|---|---|
| pipeline code | `github.com:RentschlerTobias/domain_partition_3D` | **4 commits unpushed** on `data_generation` | **no** |
| `output/` — v11, the n-sweep, 6 gen samples | local, gitignored, 4.9 GB | no | yes, hours of compute |
| compiled `HexMeshing` | Docker volume `algohex-build-cache`, 75 MB | no | yes, from public source |
| AlgoHex source | clone of `cgg-bern/AlgoHex.git` @ `3519289` | yes, upstream | — |
| Dockerfile modification | working tree only; `external/` is gitignored | no | trivially |
| `data/random_tistos/` | local, gitignored, 588 MB | no | yes, via dtOO |

**Only the first row is irreplaceable.** Everything else costs time, not
information. AlgoHex is open source, so losing the binary means rebuilding the
coinbrew chain — hours on this 2-vCPU box, minutes on 64 cores — and T2
dissolves the issue permanently by baking the binary into the image. The
Dockerfile diff is four lines that switch upstream's build off plus one that
sets `Release`; only that last line carries value and it is recorded in the
decision log.

`output/deliverable/` (625 MB) is the one worth a copy: it holds v11, v11m,
v16m and the n=2000/n=8000 structures T6 needs, and re-running those costs
hours.

An earlier draft of this document called the binary "the only one on earth".
That was wrong and is corrected above.
